## 🧭 Архитектура и ИБ-контур

```
Модуль (network_harvest_runtime.py, chaos_monkey_runtime.py, ...)
    |
    +-- gatekeeper_hub.py    <- Единый шлюз для матчей, odds, stats
    |       |
    |       +-- redis_hub.py  <- Транспорт (urllib.request / curl_cffi → Upstash REST API)
    |               +-- Circuit Breaker (Гейт 28: 10 ошибок или плоский сбой → авто-блокировка)
    |
    +-- schema_validator.py  <- Валидатор Схемы v710
    +-- value_engine.py      <- Расчет ценности линий (Value Bets)
    +-- team_registry.py     <- Алиасы команд (257+ записей)
```

*   **Zero-Folder Architecture (Root Execution / Правило 1.1):** Все исполняемые `.py` компоненты, движки, тесты и конфигурации располагаются строго на верхнем (плоском) уровне репозитория. Создание вложенных директорий для исходного кода запрещено. Единственным исключением являются конфигурации CI/CD пайплайнов `.github/workflows/`.
*   **ИБ-регламент §1.3 (Сетевой изолятор):** Использование библиотеки `requests` **категорически запрещено**. Сетевой I/O разрешен исключительно через низкоуровневый `urllib.request` и импортозамещенный `curl_cffi` для обхода TLS-фингерпринтов.

## 🔗 Модуль связывания истории и анализа (`match_linker`)

Модуль `match_linker.py` и управляющий воркфлоу `match_linker.yml` обеспечивают динамическую интеграцию оперативных Live-данных с историческими архивами и автоматическую отправку сигналов в Telegram.

### Основные функции модуля:
* **`fetch_all_history_pool()`** — выгружает весь накопительный массив исторических матчей (`history:match:*`) из Redis и сортирует его по хронологии.
* **`build_team_history_map()`** — строит историческую карту последних встреч для каждой из команд с фильтрацией по дате целевого матча (lookback до 200 игр).
* **`link_match_with_history()`** — связывает текущий матч с подготовленной историей и передает данные в `value_engine.py` для расчетов.
* **`process_upcoming_matches()`** — сканирует не завершенные матчи, запускает цикл линковки, классифицирует сигналы (`HOT`, `WARM`, `NO BET`) и формирует сводку.
* **`_send_custom_dashboard()`** — резервный механизм сборки и форматирования интерактивного HTML-дашборда для Telegram-канала.

## 🧹 Модуль очистки и балансировки памяти (`redis_flush`)

Модуль `redis_flush.py` и управляющий воркфлоу `redis_flush.yml` обеспечивают безопасную очистку, фильтрацию и балансировку кэша в облачном хранилище Redis / Upstash REST API.

### Основные функции модуля:
* **`_scan_redis()`** — осуществляет нативное сканирование базы данных с использованием `SCAN` pipelines и итерацией по курсорам. Опрашивает как standalone-ключи верхнего уровня (`history:match:*`, `system:*`, `index:*`), так и встроенные поля распределенного хэша `GatekeeperAI`.
* **`_classify_hash_fields(fields)`** — автоматически классифицирует записи хэша по категориям (матчи без котировок `K`, просроченные метаданные `stale *:meta`, поисковые индексы, системные записи).
* **`_classify_standalone(keys)`** — определяет типы независимых root-ключей для точечной очистки.
* **`_build_plan(mode, scan_result)`** — рассчитывает точный план удаления для выбранного режима.
* **`_execute_delete(to_del_hash, to_del_standalone)`** — выполняет транзакции удаления (`HDEL` батчами и `DEL` standalone-ключей) с обработкой ошибок и таймаутов.

### Доступные режимы очистки `--mode`:
* `history-only` — удаление исключительно архивных записей (`history:match:*`).
* `soft` — мягкая очистка оперативного контура (матчи без коэффициентов `K` и просроченные метаданные коллекторов `stale *:meta` старше 2 часов).
* `hard` — жесткая очистка оперативного контура с сохранением архивной истории.
* `purge` — полный сброс хранилища.
* `reset-breaker` — сброс системных флагов `Circuit Breaker` и здоровья `system:health`.

## 🔍 Модуль диагностики Propline (`check_redis`)

Модуль `check_redis.py` и управляющий пайплайн `check_redis.yml` предназначены для точечного сканирования, извлечения и детализированного аудита рыночных данных провайдера **Propline** в оперативной базе данных Redis.

### Основные функции модуля:
* **Интеграция с REST API:** Подключение к Upstash Redis через безопасный транспорт `urllib.request` в строгом соответствии с §1.3.
* **Фильтрация и поиск:** Автоматический обход глобального хэша `GatekeeperAI` с исключением архивных ключей и системной телеметрии.
* **Анализ рынков (Odds, Spreads, Totals):** Проверка полноты заполнения ключевых букмекерских секций и хронологии обновлений через апстрим (Pinnacle) в блоке `section_history`.
* **Контроль вывода:** Ограничение максимальной выборки (до 15 записей за запуск) для удобства отладки в CI/CD логах GitHub Actions.

## 📂 Окончательный реестр файлов и модулей проекта

### 🧠 Корневые исполняемые файлы и Рантаймы (Root Core Runtimes)
*   `main.py` — Главный аналитический пайплайн. На Шаге 4 производит динамический подсчет `current_errors` и извлечение `home_team`/`away_team` на плоском верхнем уровне схемы v710.
*   `gatekeeper_hub.py` — Центральный хаб экосистемы (единственный шлюз для работы с ключами вида `match:*`, правило 1.4).
*   `redis_hub.py` — Транспортный слой ядра. Работает через `urllib.request`/`curl_cffi`, реализует логику Circuit Breaker и конвертацию данных под формат `v700-prod`.
*   `network_harvest_runtime.py` — Основной рантайм сбора данных из сети. Интегрирован Гейт 28 (проверка плоской структуры фида, штраф 3 балла в Circuit Breaker).
*   `chaos_monkey_runtime.py` — Среда симуляции случайных сбоев (Chaos Engineering) для тестирования отказоустойчивости контура в реальном времени.

*   `stress_test_runtime.py` — Модуль проведения нагрузочного тестирования и проверки поведения движка при переполнении лимитов памяти.
*   `telegram_transport.py` — Транспорт отправки дашбордов и алертов в Telegram. Сетевой I/O изолирован через `asyncio.Queue` от транзакций Redis `MULTI`/`EXEC`.
*   `web_dashboard.py` — Панель управления и веб-интерфейс для мониторинга метрик и визуализации статуса экосистемы.

## ⚡ Ключевые правила разработки

1. **Плоская структура** — все `.py` файлы строго в корневом каталоге (правило 1.1).
2. **Единый хаб** — запись в Redis только через `gatekeeper_hub.py` (правило 1.4).
3. **Native transport & §1.3** — `redis_hub.py`, рантаймы и диагностика используют только `urllib.request` и `curl_cffi`. Библиотека `requests` под запретом.
4. **Circuit Breaker (Гейт 28/29)** — 10 сетевых ошибок ИЛИ обнаружение не-плоской структуры входящего фида (штраф 3 балла) → блокировка на 60 секунд с последующим авто-восстановлением.
