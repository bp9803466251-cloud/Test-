## 🧭 Архитектура и ИБ-контур

Модуль (network_harvest_runtime.py, chaos_monkey_runtime.py, ...) | +-- gatekeeper_hub.py <- Единый шлюз для матчей, odds, stats | | | +-- redis_hub.py <- Транспорт (urllib.request / curl_cffi → Upstash REST API) | +-- Circuit Breaker (Гейт 28: 10 ошибок или плоский сбой → авто-блокировка) | +-- schema_validator.py <- Валидатор Схемы v710 +-- value_engine.py <- Расчет ценности линий (Value Bets) +-- team_registry.py <- Единый движок нормализации (v10.0.1-redis-runtime)


*   **Zero-Folder Architecture (Root Execution / Правило 1.1):** Все исполняемые `.py` компоненты, движки, тесты и конфигурации располагаются строго на верхнем (плоском) уровне репозитория. Создание вложенных директорий для исходного кода запрещено. Единственным исключением являются конфигурации CI/CD пайплайнов `.github/workflows/`.
*   **ИБ-регламент §1.3 (Сетевой изолятор):** Использование библиотеки `requests` **категорически запрещено**. Сетевой I/O разрешен исключительно через низкоуровневый `urllib.request` и импортозамещенный `curl_cffi` для обхода TLS-фингерпринтов.
*   **Ручной запуск (§1.2):** Все воркфлоу экосистемы активируются строго через `workflow_dispatch`. Cron-расписания и push/pull_request-триггеры запрещены; периодичность обеспечивает `sports_pipeline.yml`.
*   **Близнецы football-data (примечание цикла #79–#80):** `FOOTBALL_DATA_API_KEY` — секрет сервиса football-data.org, в контуре НЕ используется и в Secrets не заводится; `football_data` — загрузчик истории (открытые CSV football-data.co.uk, ключ не требуется). Не путать: схожие имена — разные сущности.

## 🔗 Модуль связывания истории и анализа (`match_linker`)

Модуль `match_linker.py` и управляющий воркфлоу `match_linker.yml` обеспечивают динамическую интеграцию оперативных Live-данных с историческими архивами и автоматическую отправку сигналов в Telegram. **Статус: патчен в цикле 9.6.8** — cron удалён, чтение live-контура только через `gatekeeper_hub.get_all_matches()` (§1.4), легаси-фолбэк прямого HGETALL снят, прогоны возвращают честные коды выхода (ошибка окружения или отправки дашборда → `exit 1`).

### Основные функции модуля:
* **`fetch_all_history_pool()`** — выгружает весь накопительный массив исторических матчей (`history:match:*`): Root-ключи через `SCAN` + `GET` (`redis_command`), легаси hash-поля — как детектор незавершённой миграции; дедупликация по `canonical_id`, приоритет Root над легаси. Патчен в цикле 10.0.0-merged: прежняя реализация опиралась на несуществующие в v710 `scan_keys`/`get_history_match` (dead code — Root-скан молча пропускался).
* **`build_team_history_map()`** — строит историческую карту последних встреч для каждой из команд с фильтрацией по дате целевого матча (lookback до 200 игр).
* **`link_match_with_history()`** — связывает текущий матч с подготовленной историей и передает данные в `value_engine.py` (контракт `analyze_match()`) для расчетов.
* **`process_upcoming_matches()`** — сканирует не завершенные матчи, запускает цикл линковки, классифицирует сигналы (`HOT`, `WARM`, `NO BET`) и формирует сводку; возвращает `True/False` как результат прогона.
* **`_send_custom_dashboard()`** — резервный механизм сборки и форматирования интерактивного HTML-дашборда для Telegram-канала (лимит 4096 обеспечивает `telegram_transport`). Реализована в 10.0.0-merged: ранее вызывалась без определения — NameError глотался fallback'ом и дашборд не уходил. Отправка через контракт `send_transport_payload`.

## 🧹 Модуль очистки и балансировки памяти (`redis_flush`)

Модуль `redis_flush.py` и управляющий воркфлоу `redis_flush.yml` обеспечивают безопасную очистку, фильтрацию и балансировку кэша в облачном хранилище Redis / Upstash REST API. **Статус 10.0.0-merged:** классификатор ключей импортируется из ядра `source_diagnostics` (§1.11), транспорт переведён на `redis_command` (прямое обращение к `_execute_upstash_cmd` устранено), добавлен `--post-verify` — post-verify выполняется в том же процессе без повторного полного SCAN. Fallback-слой совместимости помечен [REVISE] до завершения миграции Шага 13.

### Основные функции модуля:
* **`_scan_redis()`** — осуществляет нативное сканирование базы данных с использованием `SCAN` pipelines и итерацией по курсорам. Опрашивает как standalone-ключи верхнего уровня (`history:match:*`, `system:*`, `index:*`), так и встроенные поля распределенного хэша `GatekeeperAI`.
* **`_classify_hash_fields(fields)`** — автоматически классифицирует записи хэша по категориям (матчи без котировок `K`, просроченные метаданные `stale *:meta`, поисковые индексы, системные записи).
* **`_classify_standalone(keys)`** — определяет типы независимых root-ключей для точечной очистки.
* **`_build_plan(mode, scan_result)`** — рассчитывает точный план удаления для выбранного режима.
* **`_execute_delete(to_del_hash, to_del_standalone)`** — выполняет транзакции удаления (`HDEL` батчами и `DEL` standalone-ключей) с обработкой ошибок и таймаутов.

### Доступные режимы очистки `--mode`:
* `history-only` — удаление исключительно архивных записей (`history:match:*`).
* `soft` — мягкая очистка оперативного контура (матчи без коэффициентов `K` и просроченные метаданные коллекторов `stale *:meta` старше 2 часов).
* `hard` — жесткая очистка оперативного контура с сохранением архивной истории.
* `purge` — полный сброс хранилища.
* `reset-breaker` — сброс системных флагов `Circuit Breaker` и здоровья `system:health`.

## ⚡ Ключевые правила разработки

1. **Плоская структура** — все `.py` файлы строго в корневом каталоге (правило 1.1).
2. **Ручной запуск** — все воркфлоу только через `workflow_dispatch` (правило 1.2); cron и push-триггеры запрещены.
3. **Единый хаб** — запись и чтение доменных данных только через `gatekeeper_hub.py` (правило 1.4).
4. **Native transport & §1.3** — `redis_hub.py`, рантаймы и диагностика используют только `urllib.request` и `curl_cffi`. Библиотека `requests` под запретом.
5. **Circuit Breaker (Гейт 28/29)** — 10 сетевых ошибок ИЛИ обнаружение не-плоской структуры входящего фида (штраф 3 балла) → блокировка на 60 секунд с последующим авто-восстановлением.
6. **Честный CI** — запрещено глушить коды возврата (`|| true`) в алертах и диагностике; утилиты обязаны завершаться `exit 1` при провале. Fake green в CI считается дефектом первого порядка.
7. **Единая сигнальная семантика** — чтение класса сигнала (`classification` → легаси-`verdict` → дефолт `NO BET`) только через `signal_contract.py`; локальные копии запрещены (§1.11).
8. **Проверяемые FIX-аннотации** — аннотация исправления обязана ссылаться на проверяемое основание (раздел гида, содержание патч-цикла); ссылка на «синхрон» без факта — дефект аудита того же порядка, что и fake green.
9. **Контракт хаба — без getattr** — доступ к методам `redis_hub`/`gatekeeper_hub` на критичных путях запрещён через `getattr` с молчаливым пропуском: несуществующая функция обязана падать на импорте, а не имитировать работу.
